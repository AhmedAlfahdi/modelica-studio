# Bug audit — 2026-09-24

Method: read every module in `src/`, then verify each suspicion against an
independent oracle rather than against the code that produced it — OpenModelica
1.27 for "is this model still valid", the plugin's own `history/` folder and
`.modelica-studio.log` for what actually happened on this machine, and the
Electron DOM harness for view behaviour. Four focused audits of the largest
untested modules ran in parallel and are folded in below.

Ranking is by consequence: **data loss first, then wrong results, then broken
features, then cosmetics.**

---

## A. Confirmed: a diagram edit deleted a declaration from the user's file

**Severity: critical — silent data loss, proved forensically.**

`sourceForSave()` returned `serializeDiagram(this.model)` whenever the diagram had
been edited (`modelOutdated`). The serializer rebuilds a class from the parsed
model, and the parsed model is a projection: components, variables, wires, free
graphics. It has no field for a nested `package Medium = ...`, an `extends`, an
`import`, an `algorithm` section, a `protected` marker, a model-level
`annotation(experiment(...))`, a declaration's description string or any comment.

Evidence, all independent of each other:

1. **The plugin's own revision store.** `history/TwoOutletTank/` holds
   `2026-09-19T02-14-50.mo` = 4227 bytes with
   `package Medium = Modelica.Media.Water.ConstantPropertyLiquidWater` and 12
   comments, and `2026-09-20T19-27-20.mo` = 1888 bytes with **no top-level
   `package Medium` declaration at all** and one comment.
2. **Byte-level reproduction.** `serializeDiagram(parse(4227-byte revision))`
   equals the 1888-byte text the plugin wrote, apart from two edits the user made
   in the studio (a moved `system` box, a changed `orifice_large.diameter`). The
   file the plugin wrote *is* the serializer's output of the edited diagram.
3. **OpenModelica.** Compiling the serialized text reproduces the user's own
   runtime error character for character:
   `[/tmp/rt/TwoOutletTank.mo:4:50-4:71] Error: Base class Medium not found in
   scope TwoOutletTank.` — the line in `.modelica-studio.log` at
   `2026-09-24T19:27:04Z` (0.3.17-era log, 09-20 entry).
4. **The log's shape.** The failure is followed 15 s later by a *successful* run
   of the same model, and the third revision (2983 bytes) carries the
   declaration plus a comment explaining why it is needed — i.e. it was re-added
   by hand afterwards.
5. **The blast radius.** Of 30 shipped examples, 3 lose description strings and
   comments on a diagram-edit save; none lose structure. The structural loss hits
   **hand-written** models, where a nested `package Medium` is the canonical
   Modelica fluid pattern.

Also confirmed by the same oracle: the rebuild silently drops `algorithm`
sections (so `y := k*pi` never runs — wrong numbers, not just a broken build),
`extends`, `imports`, `protected` markers (a protected variable is re-emitted
public), nested `model`/`function`/`record`/`connector` definitions, and emits a
bare `equation` line when a model has no equations, which is not valid Modelica.

**Fixed** in `src/modelica/text-edit.ts` (new) + `src/main.ts`:

* `patchDiagramEdits(source, model)` writes the diagram's changes into the file's
  own text. Only the declarations the diagram owns are touched (component
  instances, variables, `connect` statements, the model's own `Diagram`
  annotation); a declaration that did not change is not re-emitted, so its
  comment, formatting and description string survive. A placement move rewrites
  only the `annotation(Placement(...))`.
* It **verifies its own output** — re-parse, compare field by field against the
  model — and refuses (`undefined` + `lastPatchRefusal()`) rather than return
  text it could not confirm.
* `sourceForSave()` patches first; if the patcher refuses, it rebuilds **only**
  when the rebuild loses nothing (`structureLostBy`), and otherwise leaves the
  file alone and says so in a Notice and the trace log.
* `runSimulation`/`runSweep` now compile `sourceForSave()` — the same text Check,
  Save and note blocks compile. Previously Check said "compiles" while Simulate
  failed on a declaration the rebuild had dropped (independently found by the
  main.ts audit as finding 2).
* `test/text-edit.test.mjs`: 16 tests, including the reported loss, the
  serializer control that shows the loss is real, move/rotate/parameter/add/
  delete/rewire/graphic edits, and the two refusal paths.
* Verified against the **shipped bundle** by a bundle-level test
  (`test/bundle.test.mjs`): a drag on a model with a nested package saves the move
  and keeps the declaration and the comment.
* Verified across **43/43** real models (30 examples + 20 user models, minus 7
  with fewer than two components): every move/rotate/parameter edit patched with
  comments, descriptions, packages, `extends`, `imports`, `algorithm` and
  `protected` sections intact.

## A2. Fixed in 0.3.18: the four data-loss paths

**B1 — Revert and "Reload from disk".** `loadModelFromFile`/`loadModelFromPath`
take a `LoadOptions`; `revertToSaved` passes `{ discardStudioEdits: true }`, which
skips the flush whose whole effect was to write the studio's copy over the version
about to be read. An ordinary open still flushes (`test/bundle.test.mjs`: "opening
another model still saves the one being replaced" pins that half).

**B2 — a restart.** `modelOutdated` is persisted and restored, and the
layout-ready handler now (a) does nothing when no file was adopted — an un-saved
model's diagram is the only copy there is, and re-parsing the `model X end X;`
skeleton over it is what emptied it — and (b) when the diagram is newer than the
adopted text, keeps the diagram and leaves `modelOutdated` set, so the next save
writes those edits into the file's text.

**B3 — replacing a model.** `setModelFromSource` flushes the outgoing model by
default, so the Examples picker, a note block's "Open diagram" and a revision
restore all save first; the startup path passes `{ flushFirst: false }` because
there is nothing of the user's to save yet and a write at every launch is not
wanted. The default is the safe direction, so a caller that forgets flushes rather
than loses.

**B4 — a finished run.** `runSimulation` and `runSweep` capture the model object
they started on; after the `await` they compare identity, and a result that
belongs to a model no longer on screen is dropped with a status line and a
warning in the log, instead of being adopted and published under the new model's
name.

Each was reproduced before the fix: the three vault-level tests are run against
the pre-fix bundle and fail for the defect's own reason ("the file was not
overwritten on the way in", a missing `modelOutdated` in the payload, no write on
replacement), and the B4 test fails when its guard alone is removed and passes
when it is restored. All four pass after the rebuild.

## B. Confirmed by audit, not yet fixed

### ~~B1. "Revert" and "Reload from disk" write before they read~~ FIXED in 0.3.18
`studio-view.ts:3681` → `plugin.loadModelFromPath` → `main.ts:1834` flushes the
current model first, and for a tracked model that is `saveModelToNote()`, which
writes the studio's (to-be-discarded) text to the very path about to be read
back. So Revert keeps the drag and "Reload from disk" — the action whose whole
purpose is to protect a newer external write — destroys it. Proved with a
stub-vault probe (`writes performed: 1`; the disk copy ends up with the studio's
text). The pre-revert text survives only in `history/`.

### ~~B2. A restart discards diagram-only edits, and an un-saved model entirely~~ FIXED in 0.3.18
`data.json` stores `model` and `modelSource` but not `modelOutdated`. On the next
launch `onLayoutReady` re-parses that stale `modelSource` over the restored
diagram (`main.ts:1192-1204`), and for a model with no tracked file
`adoptSourceFromFile` does nothing, so the snapshot is discarded and then
overwritten by the next persist. Proved with a two-session probe against the
shipped `main.js`: 1 component after `loadSettings`, 0 after the layout-ready
callback.

### ~~B3. Every model-replacement path except `loadModelFromFile` skips the flush~~ FIXED in 0.3.18
`openDiagram` (`main.ts:355`), the Examples picker (`studio-view.ts:3759`) and
revision restore (`saved-models-modal.ts:338`) call `setModelFromSource`, which
replaces the model and persists with no flush and no prompt — so an un-saved
drag or a typed repair disappears silently. `loadModelFromFile` flushes and
`promptNewModel` warns, so three paths follow three different rules.

### ~~B4. A finished simulation is adopted by whatever model is open when it lands~~ FIXED in 0.3.18
`runSimulation` builds the request from the model at call time and then re-reads
the current model after the `await` (`studio-view.ts:4217`, `4236-4248`,
`4262-4280`), so switching models mid-compile attaches the old result — and the
old run log line — to the new model. `runSweep` re-reads `model.name` and
`stopTime()` on every iteration, so a switch mid-sweep sends the old source under
the new name.

### ~~B5. A sweep family outlives its model and is drawn on the next model's plot~~ FIXED in 0.3.18 — the family is dropped wherever the model changes (`forgetFamily`, called by `loadModelIntoEditor` and `reloadFromPlugin`)
`family`/`lastSweep` are cleared only by "Clear family" and by a plain Simulate.
`adoptResult` — the funnel both switch paths use — does not touch them, and
`paint` folds every family run in unconditionally, defaulting foreign names to
visible in one shared colour. Probe: after switching from A to B, B's legend
contains `kA.level · k=1` and its plot has a curve of A.

### ~~B6. Two simulations of one model share one work directory and one result CSV~~ FIXED in 0.3.18 — runs of one model are serialised (`queued`), and each run writes its own CSV, deleted after it is read
`backend.ts:291-295` keys the work directory by model name and `:472` passes one
`-r=<Name>_res.csv`; there is no lock and no per-run path, so a note block and
the studio (or two blocks with different parameter overrides) compiling the same
model at once race, and both readers get whichever CSV finished last.

### ~~B7. Reset deletes the only copy of a legacy API key~~ FIXED in 0.3.18 — `resetPreferences` keeps a legacy plaintext `apiKey`, and `mergeSettings` copies every group so the defaults cannot be edited through a live settings object
`resetPreferences` rebuilds `ai` from the defaults plus `secretName`, so a
plaintext `apiKey` still in `settings.ai` (the case the migration notice says is
preserved) is dropped and immediately written away. Related: on a first session
`mergeSettings` hands out `DEFAULT_SETTINGS`' own nested objects, so edits to
`settings.ai` mutate the defaults and a later Reset neither restores nor reports
them.

### ~~B8. Toolchain and library settings are saved but never applied~~ FIXED in 0.3.18 — the rows re-probe (`reprobeToolchain`), rebuild the index (`reloadLibrary`) or recreate the backend, and the backend is created in one place
`omcPath`, `libraryPaths`, `jobs` and `extraOmcOptions` persist and do nothing
else: `applySettingsToBackend` and `warmLibrary` each have exactly one caller,
both inside `onload`/`detectToolchain`, and the library index is memoised. So
setting the OpenModelica path after a failed detection still says "not detected"
until a restart, and adding a library path never brings its classes into the
palette.

### ~~B9. A library excluded in settings is still listed and placeable in the palette~~ FIXED in 0.3.18 — `hasPlaceableClass` and `buildPackageTree` consult `isExcluded`, so the tree and search agree
The exclusion policy is applied on the search path (`studio-view.ts:1796`) and
`listPlaceable`, but not in the palette *tree* (`addPaletteContents` →
`library.component`), so an excluded library's classes can still be dragged onto
the canvas. `library.ts`'s own comment says the tree, search, browser and
completion "all agree about what is available".

### ~~B10. The Examples menu's document listeners outlive the menu~~ FIXED in 0.3.18 — one reachable `close` for the Examples menu, used by every path including `onClose`
Choosing an example with the mouse removes the menu without calling `close()`
(`studio-view.ts:3820`), so its capture-phase `keydown` handler stays on
`document`: arrow keys are swallowed app-wide and Enter re-clicks `items[0]`,
loading a **different** example over the canvas. Closing the studio with the menu
open leaves the listeners for the app's lifetime.

### ~~B11. Sweeps are invisible to the run log, and a failure inside one is lost~~ FIXED in 0.3.18 — a sweep records a run-log entry and sets or clears the failure state and the badge, on success and on failure
`runSweep` never calls `plugin.runLog.add`, never sets or clears
`lastSimulationError` and never clears the badge or the code status — all four of
which `runSimulation` does. A failed sweep value leaves no compiler output for
"Send to AI", so that button sends the *previous* run's failure, possibly from
another model.

### ~~B12. `startTime >= stopTime` draws nothing and reports success~~ FIXED in 0.3.18 — an empty run window is refused with the reason, and a degenerate range is widened so the axis still draws
Nothing validates the window; OpenModelica answers `start=5, stop=1` with a
two-sample result at `t=[5,5]`, and `drawPlot` then divides by a zero-width x
range, so every coordinate is non-finite and the canvas drops every path and
label. The status line and run log say "2 samples" — a silent blank plot.

### ~~B13. A step cursor readout that does not match the drawn axis~~ FIXED in 0.3.18 — `timeAtPlotX` inverts the layout the plot was drawn with (the view is passed through)
`timeAtPlotX` lays the plot out without the current view (`plot.ts:254-265`)
while `drawPlot` reserves its right margin from the zoomed axis labels, so after
a zoom the reported time is off by the difference (measured ≈13 px on a two-axis
result).

### ~~B14. Two of the four paths that change a chart skip `publishChart`~~ FIXED in 0.3.18 — "Clear traces" and the double-click zoom reset publish the chart
"Clear traces" (`studio-view.ts:2447`) and the double-click zoom reset (`:3483`)
change the shared per-model chart state without publishing it, so a note's
embedded block keeps drawing the cleared traces and keeps the zoom window the
studio left behind.

### ~~B15. Saving two figures in the same minute collides~~ FIXED in 0.3.18 — a figure takes the next free name in the minute (`-2`, `-3`, …)
`figureFileName` has minute resolution and nothing else distinguishes two runs,
so the second save in a minute targets an existing file and `vault.createBinary`
is rejected: the user sees "the figure could not be saved".

### ~~B16. Neither mode button is marked active when the studio opens~~ FIXED in 0.3.18 — `syncToolbarToMode()` runs on open
`aria-pressed`/`.is-active` are only written by `syncToolbarToMode`, which runs
on a mode *change*; `onOpen` draws both buttons `aria-pressed="false"`, so the
default diagram mode looks like neither. Probe: 0 active buttons after
`await view.onOpen()`.

### ~~B17. Palette keyboard navigation uses a different order than the DOM~~ FIXED in 0.3.18 — the palette's arrow keys index the drawn rows, not the expansion order
`paletteItems` grows in the order packages were *expanded*; focus moves by index
into the *drawn* order (`:1856-1884`). Expand the second package then the first
and ArrowDown jumps into the wrong package. Probe: `paletteItems=B1,B2,A1,A2`,
`dom=A1,A2,B1,B2`, focus after ArrowDown from B1 = A2.

### ~~B18. Stop cannot abort the first AI request~~ FIXED in 0.3.18 — the abort controller is created before the first request, not per phase
`aiAbort` is null at the start of a run and during attempt 1 (`:1463`, `:1489`),
so the signal handed to `chat()` is `undefined` and Stop only takes effect
between attempts — the exact failure the surrounding comment claims to have
fixed. Probe: `attempt 1: send(signal=undefined)`.

### ~~B19. A sweep started while a run is in flight is dropped in silence~~ FIXED in 0.3.18 — a sweep that cannot start says why
The busy guard at `:3232` returns without a Notice or a status line. Because
`t_end` commits on `change` (blur) and starts a silent run, clicking Sweep while
that run is in flight discards the sweep with no explanation.

### ~~B20. Settings "Stop time" edits the open model, not the default~~ FIXED in 0.3.18 — the row is split in two: "Stop time for this model" and "Default stop time"
The row shows `plugin.stopTime()` and writes `setStopTime(n)`, so
`settings.stopTime` — the plugin-wide default, reset by Reset, and the value a
block with no model name uses — is assigned nowhere in the tree. The number shown
also changes with the open model.

### ~~B21. Toolbar tooltips never appear: `--no-tooltip` inherits~~ FIXED in 0.3.18 — `styles.css` gives `--no-tooltip` back to the children of a silenced container
`noLabelTooltip` (`a11y.ts:17-20`) is applied to every toolbar group, the mode
group and the AI row, and Obsidian shows an `aria-label` tooltip only when the
computed `--no-tooltip` on the labelled element is not `"true"`. Custom
properties inherit, so silencing the *container* silences every button inside it.
Measured with the real helper and Obsidian's own check in Electron: the child
button reports `"true"`. Since `aria-label` is deliberately the only tooltip
source here, hovering Simulate/Diagram/Generate shows nothing.

### ~~B22. The embed picker's arrow-key highlight scrolls out of view and stays there~~ FIXED in 0.3.18 — the row is scrolled by its rect against the list's rect
`scrollRowIntoView` (`embed-insert.ts:408-417`) compares the row's `offsetTop` —
measured from the modal, which has ~80 px of title, search and option rows above
the list — with the list's own `scrollTop`. Once the up-branch fires, it pins the
row at −80 px, so the highlight is invisible for every further press and Enter
inserts a row the user cannot see. Measured: rows 5, 7 and 12 all at −80.

### ~~B23. The embed picker's "Run for" value is destroyed by moving the pointer~~ FIXED in 0.3.18 — a typed span is remembered, so hovering cannot overwrite it
`pointerenter` on any row calls `select(i, false)` → `followSelection()`, which
rewrites both the chosen span and the input from the hovered row
(`embed-insert.ts:370`, `:387-394`, `:420-425`) — even though the field exists so
one note can override the span. Reaching the Height control means crossing the
list, so ordinary mouse movement wipes it. Measured: field `10`, typed `42`,
pointer enters row 4 → `14`, and the block is inserted with `time=14`.

### ~~B24. The embed Height field writes values the block's parser ignores~~ FIXED in 0.3.18 — the height field is clamped to the range the directive parser honours
The picker accepts any finite height > 0 (`embed-insert.ts:72-74`, `:287-298`),
but `parseDirective` honours only 120…2000 (`embed.ts:86-89`, `:132-135`) and
otherwise keeps its own hardcoded 320. The note then says `height=100` and the
block renders 320 — the dialog and the block disagree.

### ~~B25. The AI client sends a DeepSeek-only field to every provider~~ FIXED in 0.3.18 — the DeepSeek switch is sent only to DeepSeek; a level goes as `reasoning_effort`
Whenever thinking is off — the default — the request body carries
`thinking: {type: "disabled"}` (`ai/client.ts:74-79`), which the code's own
comment attributes to DeepSeek, while the default base URL is OpenAI's
(`ai/prompts.ts:302-314`). OpenAI rejects unrecognised request arguments with a
400, so the first request of a fresh install can fail as though the plugin were
broken. Static inference, not an observed 400 here: no OpenAI model has been
measured (`docs/ai-baseline.md`).

### ~~B26. `listModels` has no deadline, so Refresh can hang forever~~ FIXED in 0.3.18 — `listModels` has the same deadline as `chat`
`chat` was given `withTimeout` because `requestUrl` applies no timeout of its
own, but `listModels` (`ai/client.ts:156-171`) still calls it bare, and the
settings button is renamed "Asking…" and disabled until the promise settles
(`settings.ts:781-790`). Against an endpoint that accepts and never answers, the
button stays disabled for the session.

### ~~B27. The embed picker's rows announce `role="button"` but ignore the keyboard~~ FIXED in 0.3.18 — Enter and Space activate a focused picker row
`embed-insert.ts:357-371` gives each row `tabIndex`, `role` and an aria-label and
adds only `click` and `pointerenter`, so Enter and Space on a focused row do
nothing, every row is a tab stop, and the active row is not exposed. The
equivalent row in `saved-models-modal.ts:206` does handle the keyboard.

### ~~B28. One busy surface with two owners: the first operation to finish wins~~ FIXED in 0.3.18 — a busy-owner count keeps the pane marked until the last operation finishes, and a second Check is refused
`setBusy` (`busy.ts:28-36`) has no ownership or counting. `checkModel` neither
sets nor checks `this.busy` while sharing `resultsEl` with `runSimulation` and
`runSweep`, and `clearBusy` also resets the Check buttons' icons — so pressing
Check during a run clears the run's bar mid-compile, and the run's end clears a
still-running Check's spinner.

Two findings were reported independently by two audits and are listed once:
the same-minute figure collision (B15) and the revision-restore flush (B3).
